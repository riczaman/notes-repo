Part one

Testing the iManage APIs in Postman

Everything needed to call the workspace and change-event endpoints from a standing start, including how to see real response shapes before iManage has provisioned a library for us.

Target iManage Cloud (cloudimanage.com) API Universal API v2.2.26 Auth OAuth2 password grant

The provisioning problem, and the way around it

There is no iManage sandbox. Searching both the cloudimanage.com and the imanage.work/on-premises API documentation returns zero results for sandbox, trial or test environment. Every endpoint requires a provisioned hostname, a customer ID, an iManage-issued client_id and client_secret, and a service account that is permitted to log on. None of that exists for us yet.

So the plan is to build the requests now against a Postman Mock Server seeded with the exact response examples published by iManage. You get the real JSON shapes, the real field names, the real cursor formats and the real rate-limit headers today. When the vendor provisions the tenant, you change one variable and the same requests hit production.

What the mock does not prove

A mock confirms the shape of a response, not the behaviour of the server. It cannot tell you your real token lifetime, your actual rate-limit ceiling, how many workspaces a page returns under load, or whether your service account has permission for a given endpoint. Those are live-tenant questions and they are exactly what the vendor email asks about.

Setup, step by step

Seven steps. Steps 1 to 6 work today with no credentials. Step 7 is what you do the day the vendor hands over the tenant details.

  1. Install Postman

    Download the desktop app from postman.com/downloads and install it. Use the desktop app rather than the web version: the web version routes requests through a browser agent, which complicates things later when you point at an internal hostname.

    On first launch Postman asks you to sign in. Sign in. Mock servers are a cloud feature and will not work on a local-only account. A free account is enough.

    Postman's layout: Collections in the left sidebar hold saved requests. The environment selector is the dropdown in the top right and decides what {{variables}} resolve to. The main pane is the request builder, with the response appearing underneath after you press Send.

  2. Import the collection and the environment

    Click Import at the top of the left sidebar. Drag both JSON files in at once, or click Choose files and select them. Postman detects the format and imports one collection and one environment.

    You should now see iManage Work Universal API v2 — Workspace Sync under Collections. Expand it and you will find four folders. Select iManage Cloud — mock from the environment dropdown in the top right. If you skip this the requests will fail with unresolved variables.

    Worth reading first

    Every folder and every request carries a description explaining what it does and which documented constraints apply. Click a request and open the Documentation pane on the right to read it. That prose is the same material as Part two of this page, kept where you will actually be looking.

  3. Create the mock server

    Right-click the collection name and choose Mock collection. Give it a name, leave Make this mock server private unticked for now, and create it.

    Postman generates a URL that looks like https://a1b2c3d4-....mock.pstmn.io. Copy it. The mock matches incoming requests against the saved examples by method and path, and returns the matching example including its headers.

    The examples were saved against literal path values, customerId of 100 and libraryId of ACTIVE_US, and the environment ships with those same defaults so paths resolve to a match. If you change those variables before finishing your mock testing, the mock stops matching and returns a 404.

  4. Point baseUrl at the mock

    Open the environment (the eye icon next to the environment dropdown, then Edit). Replace the baseUrl current value with the mock URL you copied. Save.

    Keep the initial value as https://cloudimanage.com and only change the current value. Postman syncs initial values to shared workspaces and keeps current values local, so this way nobody else inherits your mock URL.

  5. Send the first request

    Open 1 · Authentication → Get access token and press Send. You should get a 200 with an access_token, refresh_token, token_type and expires_in.

    Open the Console at the bottom left. The test script has written the token into the authToken environment variable, and every other request in the collection sends it as X-Auth-Token automatically. You never copy and paste a token.

    Note the body type. The token endpoint takes application/x-www-form-urlencoded, not JSON. This trips people up constantly. Everything else in the API is JSON.

  6. Walk the whole flow

    Run the requests in order and watch the Console output:

    • Discovery captures customerId from data.user.customer_id and lists your libraries.
    • Get features tells you whether the tenant is cloud and whether rate limiting is enforced.
    • List workspaces returns a page and stores the cursor. Send Next page repeatedly to see paging work.
    • Get change events returns the event batch and stores the change-events cursor.
    • Create queue, then Get, Update and Delete queue to see the server-side position store.

    To see an error path, add the header x-mock-response-code: 429 to the change-events request and send it. The mock returns the rate-limited example with x-ratelimit-remaining: 0 and x-ratelimit-reset: 35. That is the response your retry logic has to survive.

  7. Switch to the live tenant

    When the vendor provisions us, fill in five environment values:

    VariableWhere it comes from
    baseUrlYour iManage hostname, e.g. https://cloudimanage.com
    clientIdIssued by iManage when the application is registered
    clientSecretIssued by iManage. Required when the client is a web application
    usernameThe dedicated service account
    passwordThe service account password

    Clear customerId and libraryId, then run Discovery first. It writes both from the live response, so you are never guessing at values.

    Credential handling

    password, clientSecret and authToken are marked as secret variable types, so Postman masks them in the UI and excludes them from exports. Do not move them to the initial-value column and do not commit an exported environment containing real values. iManage's own guidance is blunt about this: password grant "should only be used between secured endpoints such as a server-to-server process."

Reading the rate-limit headers

A test script runs on every request in the collection and logs the throttling budget to the Console. This is the single most useful habit to build early, because the polling frequency we choose has to live inside whatever ceiling iManage sets.

HeaderMeaning
x-ratelimit-remainingRequests left in the current window. As it approaches zero, slow down.
x-ratelimit-resetSeconds until the remaining count resets to full capacity.

iManage states the values differ per endpoint, so a budget observed on the change-events call tells you nothing about the workspaces call. Their guidance is monitor, adjust, retry: recalculate your rate from the headers on every response, and treat a 429 as a bug in your pacing rather than a normal condition.

Authentication

POST /auth/oauth2/token

Returns the access token that every subsequent call carries in the X-Auth-Token header. That header authenticates the caller and determines their privileges, so the integration sees exactly what the service account sees, no more.

Body is form-urlencoded. Token lifetime is configured per environment; the documented examples show 1800 and 3600 seconds but yours will be whatever the vendor sets. When it expires, call this endpoint again.

Request body

FieldTypeNotes
grant_type *enumpassword for us. Also supports authorization_code, refresh_token, urn:ietf:params:oauth:grant-type:saml2-bearer.
client_idstringRequired for all grant types except refresh token. Issued by iManage at app registration.
client_secretstringRequired if the client is a web application.
usernamestringThe service account.
passwordstringThe service account password.
customer_idintegerRequired for the SAML grant only.
Password grant constraints — quoted from the docs

"The password grant can only be used for users that are not synchronized with an external IDP, or if the IDP uses the OIDC protocol with Direct Grant support."

Separately: "The user must have a valid iManage account, and allow_logon must be true for this account."

This matches what the vendor told us. It is also the single biggest delivery risk on this integration, because it is a constraint on their identity configuration, not on our code.

Token invalidation

iManage is explicit that "a token may become invalid at any time through expiration or revocation" and that the maximum number of tokens per user is not guaranteed. The Function must treat a 401 as a signal to re-authenticate and resubmit, not as a failed run. Caching one token for its full lifetime and reacting to 401 is the right pattern; requesting a fresh token on every poll is not, and will burn the token allowance.

Workspaces — the initial synchronisation

GET /work/api/v2/customers/{customerId}/libraries/{libraryId}/workspaces

Returns a page of workspaces with their full metadata profile. This is the one-time backfill that runs before polling starts, and it is also the endpoint the vendor pointed us at.

Pagination

Use cursor paging, not offset. The iManage sample request for this endpoint is ?paging_mode=standard_cursor&limit=500&sort_order=asc&cursor=154300. Hold sort_order=asc constant so the walk is stable while the backfill runs. Keep sending the cursor from the previous response until no cursor comes back.

The workspaces cursor looks like 31653;1. The change-events cursor looks like 2687321. Different formats, different endpoints, not interchangeable. Store them in separate columns.

Filter parameters worth knowing

ParameterPurpose
custom1 … custom30The client and matter metadata fields. Which number holds what is configured per firm, so confirm the mapping with the vendor.
container_idsComma-separated workspace IDs, for fetching a known set.
edit_date, create_dateDate filters. Useful for a narrowed reconciliation rather than a full re-crawl.
totalSet true to get total_count, so you can log backfill progress against a known denominator.
limit, offset, cursor, sort_orderPaging controls.

Response envelope

{ cursor, data: { results: [], facets: {} } }. Note the workspace array is nested under data.results, not data directly, which differs from the change-events response.

Each workspace carries roughly forty fields. The ones that matter for a metadata sync are id, name, description, custom1–custom30, owner, database, edit_date, wstype and is_external.

The bulk crawl alternative

POST /work/api/v2/customers/{customerId}/libraries/{libraryId}/sync/workspaces/crawl

The vendor did not mention this one. iManage publishes a whole Sync Export collection of crawl endpoints built specifically for bulk extraction, and workspaces is one of them. It accepts cursor, limit (1 to 1000, default 100) and workspace_ids (max 50).

A limit of 1000 against the search endpoint's paging makes a material difference on a first-run backfill of a large library.

Access restriction — quoted from the docs

"Only system users of the type 'Library Migration' (WORK_MIGRATION) or 'Backup and Restore' (BACKUP_RESTORE_AGENT) can execute this request."

So this is only available to us if the vendor issues a migration-class service account. That is a question worth asking, not an assumption to build on. If the answer is no, the workspaces search endpoint does the job and the design does not change.

The same collection includes Crawl deleted events, Crawl folders, Crawl container name-value pairs and around thirty more. If the scope ever widens past workspace metadata, this is where to look first.

request body
{
  "limit": 1000,

Workspaces arrive as containers

A workspace is a container. A new workspace shows up as item_type: container, action_type: insert. Metadata edits arrive as profile_update or name_value_pair_update.

The event carries object_id and action_type only — never the new field values. To learn what changed you fetch the workspace profile separately. That is two calls per changed workspace, which matters when you size the rate-limit budget.

Change event queues

iManage can hold your read position server-side. A queue is a named bookmark storing the last event_id your application processed. Four operations, all under .../change-events/queues.

POST/…/change-events/queues

Create. Body takes queue_id (required, the queue name), event_id (optional) and filter_options (optional). Omit event_id and iManage defaults it to the latest change event for the library, which means you start at "now" and receive no history. Supply one to replay from a known point.

GET/…/change-events/queues/{queueId}

Read the current position. Returns event_id, queue_id, event_date (when the queue was last updated) and filter_options. A stale event_date makes a decent liveness check.

PUT/…/change-events/queues/{queueId}

Advance the position. Body takes event_id (required, max 254 characters) and filter_options. The response schema notes filter_options as "[Currently not implemented]", so do not design around it.

DELETE/…/change-events/queues/{queueId}

Remove the queue. Relevant for teardown or forcing a full reconciliation.

The gap in the documentation

GET /change-events takes a cursor but has no queue_id parameter, so creating a queue does not make the read automatically resume from it. The queue is a place to store a position, not a subscription.

The published change-events example returns "cursor": "2687321", which is the same format as an event id — so it appears you read the queue, pass its event_id as the cursor, and write it back with PUT. The documentation never states this. It is an inference from the example, and it is question one for the vendor.

Cursors and restart behaviour

iManage documents several pagination schemes. Change events uses explicit overflow with required cursor, described as "intended for continuous scrolling of new results. As the cursor is present even when there are no additional records, the client application may use this cursor to periodically poll for the next page."

That single property is what makes the whole polling design sound. A quiet poll still returns a cursor, so there is never a state where the Function loses its place because nothing happened.

Where the position lives

We have two places to keep it: our SQL database and the iManage queue. Use both, and treat SQL as authoritative.

  • SQL is authoritative because the commit that advances the cursor can be made atomic with the commit that writes the workspace records. A remote PUT cannot participate in that transaction.
  • The iManage queue is a mirror, updated after the local commit succeeds. It costs one extra call per cycle and gives the vendor visibility into where we are, which is useful when raising a support case.

Ordering matters

Read the batch, process it, commit the downstream writes and the new cursor in one transaction, then mirror to iManage. If you advance the cursor before the writes land, a crash in between silently drops events and nothing will ever tell you.

Getting this wrong is invisible in testing and expensive in production, which is why it is worth being deliberate about now.

Outages

As long as the cursor survives, an outage costs nothing but latency. The Function restarts, reads the stored cursor, and continues from where it stopped. No full reconciliation.

The unknown is retention: how far back the change-event journal goes. If the Function is down for a week and iManage only keeps events for 72 hours, the cursor becomes invalid and we do need a full re-crawl. That is question two for the vendor.

Rate limiting

Availability is per environment. Check rate_limiting on the features endpoint. When it is on, successful responses carry two headers.

HeaderMeaning
x-ratelimit-remainingRequests left in the window.
x-ratelimit-resetSeconds until the count resets to full capacity.

Exceeding the limit returns 429 Too Many Requests. iManage's guidance is monitor, adjust, retry: recalculate your pacing from the headers on every response, and treat a 429 as evidence the pacing logic is wrong rather than as routine.

Two documented details worth designing for

Limits differ per endpoint. The budget seen on change-events says nothing about the workspaces call. Track them separately.

Requests are retried server-side. iManage notes that requests "are continually retried by iManage until a certain period before they succeed", so a throttled request may surface to us as latency rather than an error. Set generous HTTP timeouts on the Function.

The practical consequence for polling frequency: one poll of change-events is one request, but each changed workspace adds a profile fetch. A quiet cycle costs one request; a busy cycle costs one plus the number of changes. Make the interval configurable, start conservative, and let the observed headers tell you how much room there is.

How the Azure Function uses this

A timer-triggered Function, a SQL table holding the cursor, and no webhook anywhere. That last point is not a design preference: the iManage Work Universal API has no push mechanism at all. Searching the full documentation for webhook, callback, server-sent and websocket returns nothing. Polling is the only option available, so the question is not whether to poll but how to pace it.

6Loop or sleepIf overflow is true, go again immediately. Otherwise wait for the next timer tick.
Deduplicate before fetching

A single workspace edit can produce several events — update, profile_update and name_value_pair_update in one batch. Group by object_id and fetch each profile once. On a busy batch this is the difference between staying inside the rate-limit budget and not.

The state table

One row per library. Keeping the workspaces cursor separate from the change-events cursor matters because the two formats are different and a half-finished backfill needs to resume independently of the event position.

sync stateT-SQL
CREATE TABLE dbo.ImanageSyncState (
    LibraryId            NVARCHAR(64)   NOT NULL PRIMARY KEY,
    CustomerId           INT            NOT NULL,
    QueueId              NVARCHAR(254)  NULL,
    ChangeEventCursor    NVARCHAR(254)  NULL,  -- e.g. 2687321
    BackfillCursor       NVARCHAR(254)  NULL,  -- e.g. 31653;1
    BackfillComplete     BIT            NOT NULL DEFAULT 0,
    LastSuccessfulPollUtc DATETIME2(3)  NULL,
    LastEventDateUtc     DATETIME2(3)   NULL,  -- from the newest event seen
    ConsecutiveFailures  INT            NOT NULL DEFAULT 0,
    LastErrorMessage     NVARCHAR(2000) NULL,
    UpdatedUtc           DATETIME2(3)   NOT NULL DEFAULT SYSUTCDATETIME()
);

LastEventDateUtc earns its place as a monitoring signal. Comparing it against the clock gives you sync lag in seconds, which is a far more useful alert than "the Function did not throw."

Open questions for iManage

Six things the documentation does not settle. These are the contents of the vendor email, listed here so the team can see what is still assumption rather than fact.

  1. Do the queue event_id and the change-events cursor share a namespace?

    GET /change-events has no queue_id parameter. We infer the queue's event_id is passed as the cursor, based on the published example returning "cursor": "2687321". Not documented anywhere.

  2. How long are change events retained?

    Determines whether a long outage costs latency or a full reconciliation. Undocumented.

  3. What are the actual rate limits for our tenant?

    The headers describe the budget at runtime but give no number to design a polling interval against before go-live.

  4. What type will the service account be, and is allow_logon set?

    Also whether it qualifies for WORK_MIGRATION or BACKUP_RESTORE_AGENT, which is what gates the faster crawl endpoints.

  5. Is the account outside the external IDP, or does the IDP support OIDC Direct Grant?

    Password grant fails otherwise, and that is a blocker rather than a workaround.

  6. Which custom fields hold which business values?

    custom1 through custom30 are configured per firm. We cannot map client and matter without the schema.
