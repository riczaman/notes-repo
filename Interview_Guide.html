How to play a hands-on interview

10 min

First, reframe the fear. A pension fund's hands-on round is almost never LeetCode — their own prep doc says so. It's practical: fix this bug, write a small script, query this table, explain this pipeline. They're testing whether you can work, not whether you memorized algorithms. You vibe-code daily — that means you read code, spot problems, and know what good output looks like. That's most of the job. Tonight is about converting that instinct into keyboard confidence.

The loop that makes weak coders look strong

Interviewers grade your process more than your syntax. Run this loop on every problem, out loud:

  1. Restate the problem. "So I'm getting a list of orders and I need totals per customer — is that right?" (Buys time, catches misunderstandings, looks senior.)
  2. Ask about edge cases. "Can amounts be null? Can a customer appear zero times?" Asking one good question is worth more than perfect syntax.
  3. Say the plan in plain English before typing. "I'll loop through, keep a running total in a dictionary keyed by customer."
  4. Write it messy, then clean it. A working ugly version beats an unfinished elegant one. Say: "Let me get it working first, then tidy it."
  5. Test with a tiny example. Walk one row through your code by hand, out loud.
Say this when stuck "I'd normally check the docs for the exact syntax here — the method I want does X. Can I look it up, or should I pseudocode it?" — Interviewers almost always say yes, and it reads as honest, not weak. Also good: "Let me talk through two approaches and pick one." and "I'm going to write the dumb version first."
Never do this Don't go silent for 5 minutes. Don't say "I usually just use AI for this." Instead: "My day-to-day workflow leans on Copilot-style tooling for boilerplate, so let me talk through the logic and write it out" — that frames it as modern workflow, not a gap.

What "laptop access" usually means

One or more of: a small coding task in an editor (with or without running it), debugging a broken snippet, writing SQL against a sample schema, reviewing a pull request, or whiteboard-style architecture with the laptop for reference. The sections below cover all five.

Python — the highest-yield 45 minutes

45 min

Enterprise Python interviews are 90% "take this data, reshape it." Master the dictionary-accumulator pattern below and you can solve half of everything they throw at you.

Problem 1 · The one to know cold

Group and total: sales per customer

"Given a list of order dicts, return total spend per customer, highest first."

How to think

Any "per-X" question = a dictionary keyed by X. Loop once, accumulate. Sorting a dict by value is the standard follow-up.

Code
orders = [
    {"customer": "Aviva", "amount": 120.0},
    {"customer": "Raj",   "amount": 80.0},
    {"customer": "Aviva", "amount": 45.5},
]

totals = {}
for o in orders:
    # .get(key, 0) returns 0 if the key isn't there yet
    totals[o["customer"]] = totals.get(o["customer"], 0) + o["amount"]

# Sort by value, descending -> list of (name, total) tuples
ranked = sorted(totals.items(), key=lambda kv: kv[1], reverse=True)

for name, total in ranked:
    print(f"{name}: ${total:,.2f}")
Say this out loud "Per-customer means a dict keyed by customer. I'll use .get with a default of zero so I don't need to check if the key exists. For sorting, dicts aren't ordered by value, so I'll sort the items with a lambda on the value."
Follow-ups they'll ask
  • "Top 3 only?" → ranked[:3]
  • "What if amount is missing/None?" → o.get("amount") or 0
  • "Cleaner way?" → from collections import defaultdict, then totals = defaultdict(float) and just totals[o["customer"]] += o["amount"]. Mentioning defaultdict scores points.
Problem 2 · Very common

Read a CSV, filter, report

"Here's transactions.csv with columns date, account, amount, status. Print total of all settled transactions over $1,000."

How to think

File tasks = csv.DictReader so you get dicts, not index-numbered lists. Remember: everything from a CSV is a string — convert before comparing.

Code
import csv

total = 0.0
count = 0
with open("transactions.csv", newline="") as f:
    for row in csv.DictReader(f):          # each row is a dict
        amount = float(row["amount"])       # CSV values are strings!
        if row["status"] == "settled" and amount > 1000:
            total += amount
            count += 1

print(f"{count} transactions, total ${total:,.2f}")
Traps Forgetting float() — "900" > 1000 throws a TypeError in Python 3, so you'd catch it, but comparing strings like "900" > "1000" is True and silently wrong. Also mention: "In production I'd use pandas — df[(df.status=='settled') & (df.amount>1000)].amount.sum() — but the csv module has no dependencies." Knowing both is a flex.
Problem 3 · APIs

Call a REST API properly

"Fetch users from an API and print active ones. Handle failures."

How to think

Three things separate juniors from seniors here: a timeout, raise_for_status, and not assuming the response shape.

Code
import requests

def get_active_users(base_url):
    try:
        resp = requests.get(f"{base_url}/users", timeout=10)
        resp.raise_for_status()          # throws on 4xx/5xx
    except requests.RequestException as e:
        print(f"API call failed: {e}")
        return []

    users = resp.json()
    return [u for u in users if u.get("active")]   # .get avoids KeyError

for u in get_active_users("https://api.example.com"):
    print(u["name"])
Say this out loud "I always set a timeout — without one a hung API hangs the whole job. raise_for_status turns HTTP errors into exceptions so a 500 doesn't slip through as 'success'. And I use .get('active') in case some records are missing the field."
Problem 4 · Debugging

Spot the bug — three classics

They will likely show you broken code. These three bugs cover most Python debugging questions:

Bug A · Mutable default argument
def add_item(item, items=[]):   # BUG: [] is created ONCE and shared
    items.append(item)          # between every call to the function
    return items

add_item("a")   # ["a"]
add_item("b")   # ["a", "b"]  <-- surprise!

# FIX:
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
Bug B · Modifying a list while iterating
for tx in transactions:
    if tx["amount"] == 0:
        transactions.remove(tx)   # BUG: skips elements as list shifts

# FIX: build a new list instead
transactions = [tx for tx in transactions if tx["amount"] != 0]
Bug C · Catching everything, silently
try:
    process(order)
except Exception:
    pass          # BUG: swallows ALL errors — data quietly lost

# FIX: catch what you expect, log the rest
try:
    process(order)
except KeyError as e:
    logger.warning(f"Order missing field {e}, skipping: {order['id']}")
Say this out loud "In a financial context I'd never silently swallow exceptions — a skipped record needs to be logged and ideally sent to a dead-letter queue so reconciliation can find it." (This sentence alone is worth a lot at a pension fund.)

Two-minute syntax refresher

# List comprehension: [expression for item in list if condition]
big = [t for t in amounts if t > 1000]

# Dict comprehension
by_id = {u["id"]: u for u in users}

# f-strings with formatting
f"{name}: ${total:,.2f}"      # Aviva: $1,234.50

# Sort list of dicts by a field
sorted(orders, key=lambda o: o["date"], reverse=True)

# Counting
from collections import Counter
Counter(o["status"] for o in orders).most_common(3)

SQL — four queries cover it

25 min

Sample schema they'd likely use: Customers(Id, Name), Orders(Id, CustomerId, Total, CreatedAt, Status).

Query 1 · The staple

Orders and revenue per customer — including customers with none

SELECT c.Name,
       COUNT(o.Id)              AS OrderCount,
       COALESCE(SUM(o.Total),0) AS Revenue
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id
GROUP BY c.Name
ORDER BY Revenue DESC;
Say this out loud "LEFT JOIN, not INNER, because 'including customers with no orders' means I must keep unmatched customer rows. COUNT(o.Id) counts only matched orders — it gives 0 for no-order customers, where COUNT(*) would wrongly give 1. And I wrap SUM in COALESCE because SUM of no rows is NULL, not 0."

That one paragraph demonstrates the three most-tested SQL concepts at once: join direction, COUNT semantics, NULL handling.

Query 2 · The filter-on-aggregate

Customers who spent over $10k this year

SELECT c.Name, SUM(o.Total) AS Revenue
FROM Customers c
JOIN Orders o ON o.CustomerId = c.Id
WHERE o.CreatedAt >= '2026-01-01'     -- WHERE filters rows BEFORE grouping
GROUP BY c.Name
HAVING SUM(o.Total) > 10000;          -- HAVING filters groups AFTER

The rule: WHERE runs before grouping (can't see aggregates), HAVING runs after (can). Saying that sentence is usually the whole point of the question.

Query 3 · The senior-signal

Most recent order per customer (window function)

SELECT * FROM (
    SELECT o.*,
           ROW_NUMBER() OVER (
               PARTITION BY o.CustomerId      -- restart numbering per customer
               ORDER BY o.CreatedAt DESC      -- newest first = row 1
           ) AS rn
    FROM Orders o
) ranked
WHERE rn = 1;
Say this out loud "Latest-per-group is the classic window function case: ROW_NUMBER partitioned by customer, ordered by date descending, keep row 1. Before window functions you'd need a self-join on MAX(date), which is uglier and slower."
Query 4 · Data quality

Find duplicate records

SELECT Email, COUNT(*) AS Dupes
FROM Customers
GROUP BY Email
HAVING COUNT(*) > 1;

Bonus sentence for a pension fund: "I'd wrap the dedupe itself in a transaction and keep the earliest record — in financial data you archive duplicates, never hard-delete."

Universal SQL traps NULLs never equal anything — use IS NULL, never = NULL. Any column in SELECT that isn't aggregated must be in GROUP BY. If a LEFT JOIN mysteriously "loses" rows, a WHERE clause on the right table is the culprit — move that condition into the ON clause.

React — one component pattern + bug-spotting

35 min

Enterprise React interviews test one pattern (fetch data, show it, filter it) and whether you can spot the four classic bugs. Memorize the shape of this component:

Problem 1 · The pattern to memorize

Fetch a list, handle loading & errors, add a search box

Code
import { useState, useEffect } from "react";

function CustomerList() {
  const [customers, setCustomers] = useState([]);
  const [search, setSearch]       = useState("");
  const [loading, setLoading]     = useState(true);
  const [error, setError]         = useState(null);

  useEffect(() => {
    fetch("/api/customers")
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(setCustomers)
      .catch((err) => setError(err.message))
      .finally(() => setLoading(false));
  }, []);   // empty array = run once on mount

  if (loading) return <p>Loading…</p>;
  if (error)   return <p>Something went wrong: {error}</p>;

  const visible = customers.filter((c) =>
    c.name.toLowerCase().includes(search.toLowerCase())
  );

  return (
    <div>
      <input
        value={search}
        onChange={(e) => setSearch(e.target.value)}
        placeholder="Search customers"
      />
      <ul>
        {visible.map((c) => (
          <li key={c.id}>{c.name}</li>   // key = stable unique id
        ))}
      </ul>
    </div>
  );
}
Say this out loud (the guided tour) "Four pieces of state: the data, the search text, loading, and error — so the UI can show all three situations. The effect has an empty dependency array so it fetches once on mount. I check res.ok because fetch doesn't reject on a 404. The search filter is derived during render — it doesn't need its own state or effect. And each list item gets a stable key so React can track them."
Likely follow-ups
  • "Why is search not in the useEffect deps?" — "Filtering doesn't refetch; it's computed from state I already have. Only things the fetch actually uses belong in deps."
  • "Controlled component?" — "The input's value comes from React state and updates via onChange — React owns the value, the DOM doesn't."
  • "Share this data across pages?" — "Lift it to context or use React Query — it handles caching, retries, and loading states for you."
Problem 2 · Bug-spotting

The four bugs they show everyone

Bug A · Infinite re-render loop
useEffect(() => {
  fetch("/api").then(r => r.json()).then(setData);
});   // BUG: no dependency array — runs after EVERY render,
      // and setData causes a render -> infinite loop.
      // FIX: add }, []) to run once.
Bug B · Mutating state directly
items.push(newItem);      // BUG: same array reference — React sees no
setItems(items);          // change, may not re-render.

setItems([...items, newItem]);   // FIX: new array, immutable update
Bug C · Stale state in rapid updates
setCount(count + 1);
setCount(count + 1);      // BUG: both read the same old value -> +1 not +2

setCount(c => c + 1);
setCount(c => c + 1);     // FIX: updater function gets the latest value
Bug D · Calling the handler instead of passing it
<button onClick={handleDelete(item.id)}>   // BUG: runs during render!
<button onClick={() => handleDelete(item.id)}>   // FIX: pass a function

One-line answers for concept questions

QuestionYour answer
Props vs state?Props come from the parent and are read-only; state is owned and updated by the component itself.
What is useEffect for?Side effects — anything outside rendering: fetching, subscriptions, timers. Deps array controls when it re-runs.
Why keys on lists?So React can match items across renders instead of rebuilding the whole list; must be stable and unique — not the array index if the list reorders.
What's a re-render?React calls the component function again when its state or props change, then diffs the output against the DOM.

GitHub Actions & XLR — your home turf

20 min

This is on your resume, so expect depth here. Be ready to write a workflow from scratch and to compare Actions with XLR (XL Release / Digital.ai Release).

Problem 1 · Write from scratch

CI/CD: test a Python app, deploy to Azure on main

name: ci-cd

on:
  push:
    branches: [main]
  pull_request:            # PRs get tests but NOT deploys

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: pytest

  deploy:
    needs: test                          # only after tests pass
    if: github.ref == 'refs/heads/main'  # only on main, not PRs
    runs-on: ubuntu-latest
    environment: production              # enables approval gates
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}   # never hardcode
      - uses: azure/webapps-deploy@v3
        with:
          app-name: my-otpp-app
Say this out loud "Two jobs: test runs on every push and PR; deploy needs test, is gated to main, and uses a protected environment so we can require manual approval. Credentials live in GitHub Secrets — better yet, OIDC federation with Azure so there's no long-lived secret at all." (That last clause is a strong senior signal.)
Problem 2 · Fix the broken YAML

Common breakages they plant

  • Wrong indentation — YAML dies silently on it; steps must be a list under steps:.
  • uses vs run — uses: calls a published action; run: executes shell. Mixing them up is a favorite planted bug.
  • Missing needs: — jobs run in parallel by default; without needs: test, deploy races the tests.
  • Secrets in plain text — anything that looks like a password in the YAML is the bug.
  • on: push with no branch filter — deploys on every feature branch push.

The XLR comparison talk track

"XLR (XL Release) sits above CI — it orchestrates the whole release train across teams: approval gates, change-management integration, scheduled windows, rollbacks across multiple apps. GitHub Actions owns build/test/deploy of a single repo. In my experience they complement: Actions produces the artifact, XLR governs when and how it reaches production, which matters in regulated environments like a pension plan." — Tie every answer back to governance and auditability; that's OTPP's world.

Azure OpenAI + AI Search — the RAG story

25 min

If they ask about AI, they almost certainly mean RAG — Retrieval-Augmented Generation. Learn this diagram-in-words and the two code snippets and you're covered.

The 60-second RAG explanation (memorize this)

"An LLM only knows its training data — it knows nothing about our internal documents, and asking it anyway invites hallucination. RAG fixes that in two phases. Ingestion: we take our documents, split them into chunks, run each chunk through an embedding model to get a vector, and store the vectors in Azure AI Search. Query time: the user's question is embedded the same way, AI Search finds the most similar chunks — hybrid keyword-plus-vector search works best — and we paste those chunks into the prompt as context, instructing the model to answer only from them and to cite its sources. The model never gets trained on our data; it just reads the relevant pages at question time."

Code 1

Calling Azure OpenAI (chat completion)

from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint="https://myresource.openai.azure.com",
    api_key=os.environ["AZURE_OPENAI_KEY"],   # from Key Vault, never hardcoded
    api_version="2024-06-01",
)

resp = client.chat.completions.create(
    model="gpt-4o",                  # your DEPLOYMENT name in Azure
    temperature=0,                   # 0 = deterministic; right for factual/finance
    messages=[
        {"role": "system",
         "content": "You are a helpful assistant for OTPP staff. "
                    "Answer ONLY from the provided context. "
                    "If the answer isn't in the context, say you don't know."},
        {"role": "user", "content": question},
    ],
)
print(resp.choices[0].message.content)
Code 2

Retrieve from AI Search, then answer (minimal RAG)

from azure.search.documents import SearchClient
from azure.core.credentials import AzureKeyCredential

search = SearchClient(
    endpoint="https://mysearch.search.windows.net",
    index_name="policy-docs",
    credential=AzureKeyCredential(os.environ["SEARCH_KEY"]),
)

# 1. Retrieve the top chunks relevant to the question
results = search.search(search_text=question, top=3)
context = "\n\n".join(r["content"] for r in results)

# 2. Ground the model in those chunks
resp = client.chat.completions.create(
    model="gpt-4o",
    temperature=0,
    messages=[
        {"role": "system",
         "content": "Answer only from this context. Cite the source doc.\n\n"
                    f"CONTEXT:\n{context}"},
        {"role": "user", "content": question},
    ],
)
Say this out loud "Retrieve first, then generate. I keep temperature at 0 for factual answers, tell the model to refuse when the context doesn't contain the answer, and return citations so users can verify. For search quality I'd use hybrid mode — keyword plus vector with semantic ranking — since pure vector search can miss exact terms like fund codes."

Vocabulary that makes you sound fluent

TermOne-liner
EmbeddingA vector of ~1,500 numbers capturing a text's meaning; similar meanings sit close together, which is how search-by-meaning works.
ChunkingSplitting docs into ~500-token pieces with overlap, so retrieval returns focused passages instead of whole files.
Hybrid searchKeyword + vector combined, best of both; semantic ranker re-orders the results.
TemperatureRandomness dial. 0 for factual/finance answers, higher for creative text.
Hallucination controlGrounding (RAG), "answer only from context" instructions, citations, and human review for anything binding.
Managed IdentityAzure resources authenticating to each other with no stored secrets — the answer to any "where do the keys live?" question, along with Key Vault.

If asked about responsible AI at a pension fund: data never leaves the tenant (Azure OpenAI doesn't train on your data), private endpoints, role-based access on the index so search results respect document permissions, content filters, and a human in the loop for member-facing answers.

Debugging method & mini system design

15 min

The debugging script (works on any "this is broken" task)

  1. Reproduce it. "First, let me run it and see the actual error." Never fix from theory.
  2. Read the error bottom-up. The last line of a Python traceback is the error; the frames above show the path. Say what you're reading.
  3. Shrink the problem. Comment out half, add a print/log at the boundary — "works up to here, breaks after here."
  4. State a hypothesis before changing code. "I think the amount is a string here — let me print its type to confirm."
  5. Fix, re-run, and check for the same bug elsewhere.

Narrating those five steps out loud on a debugging task is a near-guaranteed pass, even if you're slow.

The 5-minute system design template

If they ask "design an internal service" (e.g., a dashboard for fund data), walk this order:

  1. Clarify: Who uses it, how many users, how fresh must data be?
  2. Shape: React front end → REST API (Python/FastAPI or .NET) → database (Azure SQL/Postgres). Boring is good.
  3. Auth: Microsoft Entra ID (Azure AD) SSO — never build your own login.
  4. Secrets: Key Vault + Managed Identity — no credentials in code or config.
  5. Deploy: GitHub Actions CI, containers or App Service, dev → UAT → prod with approval gates (tie in XLR).
  6. Observability: App Insights logs/alerts; audit trail for anything touching member data.

At a pension fund, always spend a sentence on security, audit, and data integrity — it's the difference between a generic answer and one that fits their business.
